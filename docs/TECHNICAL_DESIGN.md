## 2. 项目背景与目标

专享楼 A 座存在多个楼层、多类教室和多时段使用需求。传统公告表或人工询问方式难以实时回答以下问题：

- 某个日期和节次有哪些教室空闲。
- 教室是否被课程或其他学生占用。
- 当前预约能否创建、取消或由管理员调整。
- 3D 楼宇中的房间状态是否与列表保持一致。
- 管理员能否用自然语言快速查询教室、课程、预约和设备信息。

本项目将教室、预约、课程、用户、通知和设备状态统一到一个前后端分离系统中，以服务端为唯一业务规则来源，以 JSON 文件作为课程项目阶段的结构化持久化介质。

## 3. 系统范围与用户角色

### 3.1 匿名用户

- 注册学生账号。
- 登录、找回密码和重置密码。
- 获取当前会话状态。

### 3.2 学生用户

- 查看指定日期和节次的脱敏全量可用性。
- 创建和取消本人预约。
- 在 Web 3D 楼宇中查看房间状态、点击房间和发起预约。
- 查看本人通知、未读数量并标记已读。
- 查看设备状态，但设备写入只允许管理员执行。

### 3.3 管理员用户

- 查询、筛选和管理全部预约。
- 调整预约时间或教室，取消和恢复预约。
- 查询账号并禁用学生账号。
- 向单个学生发送通知。
- 使用管理员专属教室信息助手。
- 控制教室空调、照明和投影状态并记录审计日志。
- 从 Web 3D 房间详情进入设备控制面板。

### 3.4 权限边界

管理员与普通用户共用登录表单，不存在独立或匿名管理员入口。前端根据角色控制页面显示，服务端再次读取会话并检查 `role === 'admin'`。任何只隐藏按钮、不在 Route Handler 中复核角色的实现都视为权限缺陷。

```text
浏览器
  ├─ 首页与登录
  ├─ 平台总览 / 预约中心
  ├─ Web 3D 数字孪生
  ├─ 通知中心
  ├─ 管理员控制台
  └─ 管理员 AI 助手抽屉
          │ HTTP / JSON / SSE
          ▼
Next.js App Router Route Handlers
  ├─ 身份认证与会话
  ├─ 全量可用性与预约规则
  ├─ 管理员预约与账号管理
  ├─ 单学生通知
  ├─ 设备状态与审计
  ├─ Web 3D 数据接口
  ├─ DeepSeek Agent 与工具调用
  └─ SSE 实时事件
          │
          ▼
业务与基础设施模块
  ├─ lib/auth.js
  ├─ lib/availability.js
  ├─ lib/booking-rules.js
  ├─ lib/realtime.js
  ├─ lib/admin-assistant.js
  └─ lib/db.js
          │
          ▼

```

系统采用前后端分离的单体仓库结构。前端通过 HTTP API 请求数据，后端通过领域函数执行业务规则，数据层负责写队列、原子替换、备份恢复和实时事件发布。

## 6. 数据模型

`.data/db.json` 是课程阶段的结构化数据文件，主要包含以下集合：

| 集合 | 关键字段 | 用途 |
| --- | --- | --- |
| `users` | `id`、`sid`、`email`、`role`、`passwordHash` | 账号与角色 |
| `sessions` | `token`、`userId`、`expiresAt` | 登录会话 |
| `bookings` | `roomId`、`date`、`segment`、`duration`、`people`、`status` | 教室预约 |
| `notifications` | `recipientId`、`senderId`、`title`、`body`、`readAt` | 单学生通知 |
| `devices` | `roomId`、空调、照明、投影、更新时间 | 教室设备状态 |
| `deviceLogs` | `roomId`、操作人、变更前后状态、时间 | 设备控制审计 |
| `assistantLogs` | 管理员、问题、回复、模型提供方、时间 | AI 助手审计 |
| `passwordResets` | 令牌哈希、有效期、使用状态 | 密码重置 |

预约记录同时保存 `createdBy`、`updatedBy`、`createdAt` 和 `updatedAt`，用于追踪创建与调整来源。

## 7. 核心业务流程

### 7.1 注册、登录与会话

1. 注册接口验证学号、邮箱和密码格式。
2. 密码使用随机盐和 `scryptSync` 哈希后写入数据库。
3. 登录成功后生成随机会话令牌，写入 `HttpOnly`、`SameSite=Lax` Cookie。
4. 当前用户接口根据 Cookie 读取会话，返回角色和公开账号信息。
5. 生产环境启用 `Secure` Cookie；密码重置后使该用户全部旧会话失效。

### 7.2 全量教室可用性

学生打开平台后，前端同时请求本人预约和指定日期、节次的全量可用性。

`GET /api/bookings/availability` 返回脱敏后的房间列表：

- 不返回其他学生的姓名、学号、邮箱和联系方式。
- 其他用户预约显示为 `reserved`。
- 当前用户预约显示为 `mine`。
- 课程占用显示为 `class`。
- 未预约房间显示为 `free`。
- 维护或关闭房间分别显示为 `maintenance` 或 `closed`。

前端根据这份数据同时更新教室列表、统计卡片和 Web 3D 房间颜色。

### 7.3 创建预约

```text
用户提交教室、日期、节次、时长、用途和人数
  → POST /api/bookings
  → 读取服务端会话
  → validateBooking 校验日期、时间、人数和房间
  → 在 mutateDb 写锁内检查课程与预约重叠
  → 写入 db.json
  → 原子替换文件
  → 发布 db:changed
  → SSE 推送给在线页面
```

关键点是创建预约时重新检查冲突，不信任前端传来的“空闲”判断。

### 7.4 取消和管理员调整

- 学生只能取消本人有效预约。
- 管理员可以取消、恢复、调整时间和更换教室。
- 调整预约时忽略当前预约自身的重叠，但继续检查课程和其他预约。
- 取消后的记录保留状态，不参与后续冲突检测。

### 7.5 实时刷新

数据写入成功后，`lib/db.js` 发布 `db:changed` 事件。登录用户通过 `/api/realtime` 建立 SSE 连接，浏览器收到事件后刷新可用性、本人预约、通知和管理数据。

前端保留 60 秒低频兜底查询。SSE 正常时，预约、取消、管理员调整、通知和设备状态变化无需手动刷新。

### 7.6 通知闭环

最终产品只保留管理员向单个学生发送通知：

1. 管理员选择接收学生并提交通知。
2. 后端验证发送者和管理员角色。
3. 通知写入 `notifications`。
4. 学生通过 `/api/notifications` 查询本人通知。
5. 学生可以标记已读，界面显示未读数量。

信箱和全体通知已从产品范围撤销，不作为最终功能。

### 7.7 找回密码

`POST /api/auth/recover` 验证学号和校园邮箱，生成随机令牌，只在数据库中保存 SHA-256 哈希。令牌默认有效期为 30 分钟。

- 配置投递网关时，由服务端向邮件或企业通知渠道发送重置地址。
- 开发环境可返回测试令牌，便于本地演示。
- 生产环境默认拒绝明文返回令牌。
- 重置成功后更新密码并注销全部旧会话。

### 7.8 设备控制

管理员可以控制空调、照明和投影，并应用上课、自习、节能、全关四种场景。每次修改写入 `deviceLogs`，刷新页面后从后端重新读取。

当前实现是可验证的软件控制闭环，不代表已经连接真实楼宇硬件。接入 MQTT、Modbus 或厂商 SDK 时，可替换执行层并保留现有权限、校验和审计模型。

## 9. 服务端预约规则

所有预约接口统一调用 `lib/booking-rules.js`：

1. 日期必须是有效的 `YYYY-MM-DD`，不能早于当前日期。
2. 起始节次必须是 1 至 6。
3. 时长必须是 1 至 4 个节次，且不能超出当天开放范围。
4. 当天已经开始的节次不能预约。
5. 人数必须是正整数，且不能超过教室容量。
6. 预约不能与课程安排重叠。
7. 预约不能与其他有效预约重叠。
8. 取消记录不占位；管理员调整预约时忽略自身。

Agent 中的节次块定义为：

| 节次值 | 时间块 |
| --- | --- |
| 1 | 第 1 至 2 节 |
| 2 | 第 3 至 4 节 |
| 3 | 第 5 至 6 节 |
| 4 | 第 7 至 8 节 |
| 5 | 第 9 至 10 节 |
| 6 | 第 11 至 12 节 |

## 10. JSON 持久化与并发控制

课程项目使用本地 JSON 保存结构化数据，但不再采用“直接覆盖整个文件”的方式。数据层实现：

- 进程内 Promise 队列，将读、写和变更串行化。
- `mutateDb` 在同一临界区完成读取、修改和落盘。
- 先写临时文件，再通过原子替换更新正式文件。
- 每次写入前保留上一版为 `db.backup.json`。
- 解析失败时保留损坏文件，优先尝试从备份恢复。
- 兼容早期数据，缺少的集合自动补齐。

该方案能够覆盖单实例 Node 进程下的并发预约，但多实例部署仍需数据库事务或分布式锁。

## 11. Web 3D 与 AI 助手概览

### 11.1 Web 3D

业务 3D 使用真实房间数据构建楼层和房间，颜色来自全量可用性接口，支持悬停、点击、详情查看、预约入口和管理员设备控制。装饰性 GLB 模型只负责环境效果，延迟加载并可通过环境变量关闭。

详细设计见《特色技术补充说明》。

### 11.2 AI 模型 API

管理员助手通过 DeepSeek Chat Completions API 接入模型，并使用服务端工具读取实时教室数据。模型只回答教室预约领域问题，不得直接写数据库。预约和取消必须经过“动作预览、管理员确认、服务端复核、业务写入”四步。

详细领域限制见《特色技术补充说明》第 3 章。

## 12. 安全与隐私

- 密码只保存 scrypt 哈希，不保存明文。
- 会话令牌通过 HttpOnly Cookie 传递。
- 所有管理员接口在服务端复核角色。
- 全量可用性接口不返回其他用户 PII。
- AI 工具不返回密码、会话令牌和 API Key。
- 外部模型密钥只保存在服务端 `.env.local`，发布包排除该文件。
- 设备控制和助手确认执行都重新验证管理员身份。
- 发布 ZIP 需要检查是否误带 `.env.local`、真实密钥、`.next` 或 `node_modules`。

当前课程版本尚未实现企业级 CSRF 令牌、速率限制和密钥托管。正式上线时应补齐这些安全能力。

## 16. 已知边界与后续改进

1. 当前数据层适合课程项目和单实例演示，不适合多实例高并发生产。
2. 设备控制尚未连接真实空调、照明、投影和楼宇网关。
3. 摄像头监控在未配置真实视频源时明确显示未接入，不伪造 `LIVE`。
4. AI 助手依赖外部模型可用性，但具备本地实时数据回退。
5. 正式上线需要补充 CSRF、速率限制、审计脱敏和密钥托管。
6. 多实例部署需要分布式锁或数据库事务。
7. 后续可增加 RAG 政策知识库、工具轨迹重放和模型效果评测。
