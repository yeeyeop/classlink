# Vibe 日志 03：SSE 实时刷新、账号管理与单学生通知

## 本次目标

让教室空闲数量、预约状态、设备状态和账号数据在发生变化后自动刷新，不再要求现场手动刷新。同时修正通知的发送与接收逻辑：管理员发送测试通知后，学生端必须有可查询、可标记已读的收件路径。

## 使用提示词

> 我希望教室空闲数量、使用状态、预约和管理数据变化后自动更新，不要每次手动刷新。先判断是否真的需要 WebSocket，再选择适合当前单实例 JSON 架构的实时方案。测试时要能明确看到哪个写入触发了哪个页面更新。通知要形成真实闭环，发送者不能被误显示成接收者；信箱和全体通知不适合当前范围，撤掉它们，只保留管理员向单个学生发送通知。

## AI 生成结果

- 数据层在原子落盘成功后发布 `db:changed` 事件。
- 新增带登录校验的 `/api/realtime` SSE 接口，学生总览显示连接状态。
- 页面收到事件后以防抖方式刷新可用性、本人预约和通知，管理台同步刷新预约与账号列表。
- 保留 60 秒低频查询作为断线兜底，避免网络中断后长期停留在旧状态。
- 通知模型区分发送者和接收者，学生端增加本人通知查询、未读数和标记已读。

## 遇到的问题

第一轮方案容易走向前端高频轮询，既增加请求量，又不能保证操作后立即看到变化。通知页面曾经把发送者和接收者展示混在一起，管理员发送的消息看起来像“高杨发送、管理员也收到”；这不是数据丢失，而是查询边界和界面语义混乱。撤销信箱和全体通知时，前端刷新逻辑还出现过预约入口暂时不可用，需要通过真实请求重新定位是筛选状态还是接口回归。

## 迭代修改

- 实时通道选择 SSE：当前主要是服务端单向推送，浏览器原生支持自动重连，逻辑比 WebSocket 更小。
- 只在预约、账号、设备和单个学生通知等业务写入后发布事件，助手日志和会话心跳不触发无意义的教室刷新。
- 删除信箱和全体通知入口，保留管理员向单个学生发送通知的闭环。
- 通知查询始终以当前会话用户为接收者，管理员只负责发送和查看审计记录。
- 修复预约回归后，用两个浏览器会话重新验证：学生 A 写入后，学生 B 的可用性卡片自动变化。

## 小组理解

实时刷新不是“定时多请求”，而是业务事件驱动的一致性策略。SSE 适合当前单实例部署；若未来部署多实例，需要把进程内事件总线替换成 Redis Pub/Sub，但前端协议可以不变。

## 验证证据

- `/api/realtime` 返回 `text/event-stream`，冒烟测试收到连接事件。
- 预约写入后页面自动刷新，无需按 F5。
- 管理员调整或取消预约后，学生总览状态同步变化。
- 学生通知接口返回 200，发送者与接收者展示分离。
- 信箱和全体通知相关入口与接口不再作为最终功能出现。
