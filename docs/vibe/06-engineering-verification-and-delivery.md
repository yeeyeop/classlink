# Vibe 日志 06：工程测试、性能降级与最终交付

## 本次目标

把“能运行”提升到“能复现、能解释、能演示、能安全提交”。需要补齐测试、Lint、构建和真实 HTTP 冒烟验证，修复 JSON 并发与损坏恢复风险，降低大模型资源对首屏的影响，整理课程要求的文档、Vibe 日志、答辩材料和最终 ZIP。

## 使用提示词

> 不要只说构建通过。请真实启动生产服务，走登录、预约、冲突、取消、通知、密码重置、管理员和助手接口。浏览器里检查 3D、实时刷新和预约交互。把评分标准转成材料清单，整理 README、技术设计、分工、Vibe、测试用例、特色技术说明和答辩讲稿。打包时绝不能包含 `.env.local` 或 DeepSeek Key，并告诉我别人拿到压缩包后是否需要重新配置模型。

## 遇到的问题

原始项目没有测试和 Lint，依赖审计还发现旧版 Next.js 的高风险漏洞。另一个风险是材料与实现漂移：撤掉信箱和全体通知后，旧 Vibe 日志仍把它们写成最终功能，必须在交付前统一。打包时还可能出现“.env.local 被带入 ZIP”这种低级但严重的安全问题，因此不能只靠 `.gitignore`，还要对压缩包内容做独立检查。

## 迭代修改

- 验证标准从“页面能打开”改为“真实服务启动、真实 HTTP 请求、真实数据变化”。
- 浏览器中检查 3D 画布、房间点击、预约按钮和取消后的状态恢复，不只检查 DOM 文本。
- 清理过时日志，最终保留六条与当前实现一致的 Vibe 日志。
- 发布前运行单元测试、Lint、生产构建、冒烟测试和依赖审计。
- 对 ZIP 检查 `.env.local`、真实 Key、`.next` 和 `node_modules` 是否存在；发布包未包含密钥，其他人使用 AI 助手时需要自行配置 `.env.local`。

## 小组理解

工程交付不是最后复制几份文档，而是把需求、代码、数据流、测试和人工判断连成可追溯的证据链。一个功能能被演示，只是结果；能说明它为什么有效、失败时怎么恢复、别人如何复现，才是完整交付。
