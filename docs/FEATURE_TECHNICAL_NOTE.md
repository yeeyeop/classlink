# CLASSLINK 特色技术补充说明

版本：最终提交版 1.0  
日期：2026-09-10  
项目名称：CLASSLINK 专享楼 A 座空教室预约平台

## 1. 特色技术选择与评分目标

课程介绍将 95 分档定义为“标准项目 + 1 项特色技术深度集成”，并强调：

- 特色技术不能只是功能堆砌或装饰。
- 特色技术必须连接真实后端数据或真实外部服务。
- 后端数据变化应能更新前端展示。
- 用户操作应形成可验证的数据闭环。
- 去掉该技术后，项目核心价值应明显下降。

本项目选择两项与核心业务直接关联的特色技术：

1. Web 端 3D 楼宇与智慧教室可视化。
2. AI 模型 API 集成与领域受限 Agent。

两项技术不是独立展示页：

- Web 3D 读取真实教室、课程和预约状态，并支持点击预约与管理员设备控制。
- AI 助手读取同一套实时数据，通过工具调用回答教室问题，并在管理员确认后执行预约或取消。
- 两项技术共享鉴权、业务规则、JSON 数据和 SSE 实时事件，构成一个系统内的两条交互入口。

## 2. 特色技术一：Web 3D 楼宇与智慧教室

### 2.1 技术定位

系统中的 3D 分为两层：

| 层级 | 实现 | 定位 |
| --- | --- | --- |
| 业务数字孪生 | `CampusDigitalTwin.jsx` 程序化几何 | 映射真实楼层、房间和业务状态 |
| 装饰性 3D 背景 | `ModelBackground.jsx` 与 GLB | 提升首页视觉表现，不承担业务事实 |

这种分层是刻意的。旧版 GLB 动画没有稳定的房间 ID 映射，点击模型也无法确定对应教室，因此不能证明“3D 数据深度集成”。最终方案使用真实房间数据生成业务空间，GLB 只作为可选环境层。

### 2.2 与课程深度集成标准的对应

| 课程要求 | 本项目实现 | 可验证证据 |
| --- | --- | --- |
| 3D 不是孤立装饰 | 房间几何由真实 `initialRooms` 数据生成 | `CampusDigitalTwin.jsx` |
| 教室信息来自后端 | 状态来自 `/api/bookings/availability` | 浏览器网络请求与颜色变化 |
| 点击空间查看详情 | Three.js Raycaster 拾取房间 | 可选中 `3F · 314` |
| 后台变化更新 3D | SSE 收到数据变更后刷新可用性并更新场景 | 预约后颜色和详情变化 |
| 与业务流程连接 | 空闲房间可预约，管理员可进入设备控制 | UI 预约、取消和设备面板 |
| 数据可解释 | 每种颜色对应明确状态枚举 | 状态映射表 |

### 2.3 前端结构

```text
真实房间定义
  → 当前日期和节次
  → GET /api/bookings/availability
  → allRoomStates
  → CampusDigitalTwin
  → Three.js 房间网格
  → Raycaster 点击
  → 教室详情面板
  → 学生预约 / 管理员设备控制
```

页面不自行猜测房间是否空闲。预约、课程和维护状态都由后端返回，前端只负责渲染和交互。

### 2.4 状态映射

| 后端状态 | 3D 颜色 | 业务含义 |
| --- | --- | --- |
| `free` | 绿色 | 当前时段可预约 |
| `class` | 黄色 | 教务课程占用 |
| `reserved` | 浅蓝色 | 其他用户已预约 |
| `mine` | 蓝色 | 当前用户已预约 |
| `maintenance` | 灰色 | 教室维护 |
| `closed` | 深灰色 | 不开放预约 |

图例数量由当前房间状态实时汇总，不使用随机颜色或模拟数据。

### 2.5 点击、选中和视角保持

用户提出过一个典型交互问题：点击教室后，如果数据刷新导致整个场景重建，选中会回到初始状态。最终实现将“场景重建”和“选中样式更新”分开：

- 只有房间 ID 集合变化时才重建空间。
- 可用性变化时只更新材质、描边和缩放。
- 选中房间保持高亮。
- 数据刷新不重置用户当前视角和选中对象。

该设计保证实时更新和连续交互可以同时存在。

### 2.6 实时联动

预约或取消的数据路径为：

```text
用户点击预约
  → POST /api/bookings
  → 服务端检查冲突和课程
  → JSON 原子写入
  → 发布 db:changed
  → SSE 通知所有在线页面
  → 重新请求可用性
  → 3D 房间颜色和详情更新
```

管理员调整教室后，原教室恢复为新的真实状态，目标教室变为占用状态，学生端无需刷新。

### 2.7 装饰性 GLB 的作用与降级

`ModelBackground.jsx` 保留 GLB 环境效果，但采用以下策略：

- 默认开启，满足现场视觉演示。
- 在浏览器空闲后分阶段加载，不阻塞首屏交互。
- 弱网或低性能设备可设置 `NEXT_PUBLIC_ENABLE_GLB_BACKDROP=false`。
- 业务 3D 使用程序化几何，不依赖 GLB 文件是否存在。

因此，即使约 40 MB 的装饰资源关闭，教室数字孪生、点击和预约仍然可用。

### 2.8 实际验收结果

- 3D 画布尺寸为 400 × 645，非空像素分布正常。
- 浏览器可实际点击并选中 `3F · 314`。
- 选中后详情面板显示楼层、房间号、类型、容量、课程和状态。
- 通过界面预约 205 教室后状态更新，取消后恢复。
- 可用性刷新不会把选中状态重置为初始值。

### 2.9 去掉 Web 3D 后的影响

如果删除 Web 3D，系统仍可使用二维列表预约，但会失去：

- 楼层和房间的空间认知。
- 一眼识别整栋楼占用分布的能力。
- 点击空间直接查看教室和预约的操作路径。
- 管理员从房间详情进入设备控制的联动入口。

因此，去掉 Web 3D 会明显降低系统的可视化和管理价值，符合特色技术判定标准。

## 3. 特色技术二：AI 模型 API 与领域受限 Agent

### 3.1 技术定位

管理员需要通过自然语言快速确认以下信息：

- 某个时间有多少空闲教室。
- 指定教室是否被课程或预约占用。
- 当前预约人、课程和设备状态。
- 管理员准备执行的预约或取消动作是否合法。

系统在主页右侧提供管理员专属 AI 助手抽屉，使用 DeepSeek Chat Completions API。助手不是独立聊天页面，而是与预约、课程、设备和权限系统共用服务端数据。

### 3.2 实际模型与接口说明

项目通过 OpenAI 兼容的 Chat Completions 接口接入 DeepSeek：

```env
DEEPSEEK_API_URL=https://api.deepseek.com/chat/completions
DEEPSEEK_MODEL=deepseek-chat
DEEPSEEK_TIMEOUT_MS=30000
```

配置中使用 `deepseek-chat` 作为兼容模型别名。实际验收请求的响应中包含 `model: "deepseek-flash"`，文档按真实响应记录，不把别名写成未经核实的模型版本。

本项目没有重新训练大模型，也不是把普通聊天接口直接嵌入页面。领域能力通过以下四层实现：

1. 领域系统提示词。
2. 只读实时数据工具。
3. 服务端工具执行和参数校验。
4. 写操作两阶段人工确认。

### 3.3 AI 领域限制总览

AI 助手的领域限制是本项目的核心设计之一，分为九个层次：

| 限制层 | 目的 | 实现方式 |
| --- | --- | --- |
| 话题范围 | 防止助手变成通用闲聊工具 | 系统提示词只允许教室、预约、课程、设备、规则 |
| 数据来源 | 防止模型编造教室状态 | 所有事实必须来自服务端工具 |
| 工具白名单 | 防止模型调用未授权能力 | 只注册教室相关工具 |
| 写权限 | 防止模型直接改数据 | 模型只能生成动作预览 |
| 角色权限 | 防止学生使用管理助手 | UI、组件和 API 三重检查 |
| 数据最小化 | 防止敏感信息进入模型 | 不发送密码、令牌、API Key 和会话 |
| 对话轮次 | 防止工具循环和无限请求 | 最多 4 轮工具调用 |
| 超时回退 | 保证外部模型失败时仍可查询 | 30 秒超时后回退本地规则 |
| 审计留痕 | 支持答辩时解释真实调用 | 保存问题、回复、提供方和时间 |

### 3.4 领域限制一：话题白名单

助手允许回答的内容只有：

- 教室楼层、类型、容量、设施和空闲状态。
- 当前日期和节次的课程安排。
- 有效预约和预约时间。
- 空调、照明和投影状态。
- 预约规则和可操作建议。
- 预约或取消动作预览。

系统提示词明确要求模型不要回答代码、娱乐、医疗、法律、闲聊等问题。即使模型误判话题，服务端工具也不能越权，因为没有对应工具可以执行。

### 3.5 领域限制二：无关话题的自然收束

早期版本对其他话题生硬拒答，用户体验不好。最终行为统一为：

> 我们还是接着说和教室预约相关的吧。

然后模型可以继续提示管理员查询空闲教室、课程、预约或设备状态。该行为不是预设关键词匹配，而是在领域提示词和模型对话中完成的。

实际测试：

| 用户输入 | 实际行为 |
| --- | --- |
| “今天晚饭吃什么？” | 回复“我们还是接着说和教室预约相关的吧。” |
| “找适合 10 人以上的空闲教室” | 调用 `search_rooms` |
| “查看 205 教室状态” | 调用 `get_room` |
| “预约 208，明天第 3 至 4 节” | 生成待确认预约动作 |
| “取消我的 208 预约” | 生成待确认取消动作 |

### 3.6 领域限制三：事实必须来自工具

模型不能凭记忆生成教室状态。服务端在每轮对话中提供当前日期和节次，并按需执行以下工具：

| 工具 | 类型 | 作用 |
| --- | --- | --- |
| `search_rooms` | 只读 | 按楼层、类型、容量和状态筛选教室 |
| `get_room` | 只读 | 查询指定教室的预约、课程和设备 |
| `list_courses` | 只读 | 查询当前时段课程 |
| `list_reservations` | 只读 | 查询当前时段有效预约 |
| `get_device_status` | 只读 | 查询教室设备状态 |
| `get_booking_rules` | 只读 | 返回预约规则和节次映射 |
| `prepare_booking` | 预览 | 生成待管理员确认的预约动作 |
| `prepare_cancel_booking` | 预览 | 生成待管理员确认的取消动作 |

模型输出的房间号、预约人或设备状态必须来自工具结果。若工具没有返回数据，助手应说明无法确认，而不是补造答案。

### 3.7 领域限制四：模型不能直接写数据库

系统采用两阶段执行：

```text
管理员输入自然语言
  → 模型选择 prepare_booking / prepare_cancel_booking
  → 服务端生成动作预览
  → 前端显示确认卡片
  → 管理员点击“确认执行”
  → POST /api/admin/assistant/actions
  → 服务端重新检查管理员角色
  → 重新检查日期、节次、课程和预约冲突
  → 写入数据库
  → SSE 通知其他页面
```

模型没有直接调用 `/api/bookings` 或修改 JSON 的权限。即使模型被提示词诱导，也只能返回一个未执行的动作建议，最终写入仍由管理员按钮触发。

### 3.8 领域限制五：管理员权限边界

AI 助手只允许管理员使用：

- 主页面拉手和抽屉只在 `session.role === 'admin'` 时渲染。
- `AdminAssistant` 组件自身再次检查会话。
- `/api/admin/assistant`、日志接口和 `/api/admin/assistant/actions` 全部在服务端检查管理员角色。
- 普通学生调用上述接口返回 403。

这避免了“前端隐藏但接口公开”的假权限控制。

### 3.9 领域限制六：敏感数据最小化

模型上下文只包含业务所需信息：

- 允许：房间、状态、课程、预约人姓名、人数、设备状态和规则。
- 禁止：密码哈希、会话令牌、密码重置令牌、API Key、Cookie 和服务端环境变量。

管理员需要知道预约人才能管理现场，但助手不会获得登录凭据或修改账号的能力。

### 3.10 领域限制七：工具轮次和模型失败保护

- 每轮请求最多执行 4 次工具调用，防止模型循环。
- DeepSeek 请求默认超时 30 秒。
- 未配置模型 Key 时使用本地实时数据规则。
- 外部接口超时或返回异常时，服务端回退到本地答案并在响应中标记 warning。
- 回退答案仍读取真实数据，不返回伪造的空结果。

### 3.11 领域限制八：审计日志

每次成功问答写入 `assistantLogs`，记录：

- 提问管理员。
- 用户问题。
- 助手回复。
- 模型提供方和模型标识。
- 生成时间。

日志保留最近 200 条，供管理员查看并用于答辩解释。

## 4. AI Agent 数据流

```text
管理员提问
  → POST /api/admin/assistant
  → 服务端验证管理员角色
  → buildAdminAssistantContext 读取实时业务数据
  → DeepSeek 生成回答或工具调用
  → 服务端按白名单执行工具
  → 工具结果返回模型
  → 生成领域受限中文回答
  → 写入 assistantLogs
  → 前端显示回复或动作确认卡片
```

预约和取消动作不会在该数据流中直接落盘，而是等待管理员确认后进入独立的业务写接口。

| --- | --- |
| DeepSeek API 已真实调用 | 自然语言请求进入模型并返回 |
| 工具调用 | “10 人以上空闲教室”触发 `search_rooms` |

## 6. 去掉 AI 模型 API 后的影响

如果删除 AI 助手，管理员仍可在管理台手动筛选预约，但会失去：

- 用自然语言快速确认教室和课程状态的能力。
- 跨预约、课程和设备数据自动汇总。
- 面向领域工具调用和人工确认的 Agent 工作流。
- 管理员现场运营效率提升的直接入口。

因此，AI 模型 API 不是“页面上多一个聊天框”，而是管理业务的数据查询与操作辅助层。

## 8. 答辩演示建议

### 8.1 Web 3D 演示

1. 打开平台总览，展示教室状态统计。
2. 点击 3D 房间 `3F · 314`，展示详情不重置视角。
3. 预约空闲房间，观察颜色和状态更新。
4. 取消预约，观察恢复为空闲。
5. 用管理员账号从房间详情打开设备控制面板。

### 8.2 AI 助手演示

1. 使用管理员账号打开主页面右侧助手。
2. 问“今天第 3 至 4 节还有多少空闲教室”。
3. 问“205 教室现在是什么状态”。
4. 输入无关问题，展示自然收束。
5. 让助手准备预约，指出尚未执行。
6. 点击确认执行，展示真实数据库和 3D 状态更新。
7. 用学生账号确认助手入口不存在，直接请求接口返回 403。

### 8.3 常见答辩问题

**问题：为什么不直接让模型修改数据库？**  
因为大模型输出具有不确定性。系统让模型负责理解和生成动作，让服务端负责权限、规则和最终写入，管理员确认是必要的安全边界。

**问题：为什么节次是 1 至 6，而不是 1 至 12？**  
Agent 使用节次块，1 至 2 为第 1 块，依此类推。页面和预约规则统一使用块编号，展示时可以映射为第 1 至 12 节。

**问题：为什么 GLB 模型关闭后 3D 还能用？**  
因为业务 3D 不依赖 GLB，而是由真实房间数据生成。GLB 只承担环境氛围，关闭后不影响预约和状态联动。

**问题：AI 能回答无关问题吗？**  
系统允许自然对话，但会主动收束到教室预约领域。即使模型误判，工具白名单、服务端校验和确认执行也会阻止越权操作。
